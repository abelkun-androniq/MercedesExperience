# Evo II and W 196 R component airflow implementation proposal

Replace the Evo’s two whole-car airflow views with three experiments, **rear wing → front splitter → front wheel arch**. Replace the W 196 R centre-line tunnel with one **enclosed / exposed front wheel** experiment. The museum photo locates each part. Scrolling brings it into close-up. One tap should reveal something the air does, even with the animation paused.

The deliverable is four component steps, their offline data, English and Hungarian copy and tests. The Evo’s road-car comparison moves into its background note. The W 196 R’s straight-line estimate can go in its technical facts, labelled as a separate calculation. Both engine steps follow the airflow experiments. ### A. Reproduce the wing reference

1. From the repo root check for `tools/cfd/evo2.glb` and `tools/cfd/out/{base,flap}-{28,40}.{json,bin,solid}`. The mesh and raw outputs are ignored by Git. This checkout has them. A clean checkout can run the published site from its committed assets. To regenerate a missing reference volume with the original mesh, use e.g. `node tools/cfd/run.mjs flap 28 9000`. Repeat only the missing case/grid pairs. Use the recorded mesh credit. If a required volume and the source mesh are both missing, mark the wing reference export pending. Exercise playback on the small test fixture while continuing the splitter and wheel work. Reproducing the off-centre probe requires the original velocity components. [Ignored inputs](../tools/cfd/.gitignore) · [Mesh source and transform](../tools/cfd/mesh.mjs)
2. Add an offline entry point, proposed as `tools/cfd/part.mjs`. Have `node tools/cfd/part.mjs wing reference` read the two base/flap pairs, sample the probe, and write the 28 mm display crop under the ignored `tools/cfd/out/wing-reference/`. Refactor the raw reader out of the existing exporter if sharing it. Importing it must have no write side effects. Keep the original whole-car commands usable. [Volume layout and reader](../tools/cfd/export.mjs)
3. In a raw 3-D file the four Float32 blocks are density, rearward velocity, lateral velocity and upward velocity. For `N = nx * ny * nz`, the cell offset is `(k * ny + j) * nx + i`. Its centre in mm is `[x0 - (i + 0.5)*h, (j + 0.5)*h, (k + 0.5)*h]`. Check for `16*N` bytes of field data and `N` mask bytes. Average the rearward and upward velocities over **x −3920…−3750, y 200…300, z 1230…1290 mm**. Compute `atan2(meanUp, meanRearward)` in degrees. Expect 48 fluid cells on the fine grid and 12 on the coarse grid, with the four angles above. Use actual rearward flow as the arrow’s horizontal direction.
4. Recreate the figure’s 28 mm crop by selecting cell centres in **x −4300…−3150 and z 810…1420 mm**, at **y = 238 mm**. This yields 41 columns × 22 rows. Its first column / bottom row centre is `[-3171, 238, 826]` mm. Colour by vertical speed divided by inlet speed, on the same −0.25…+0.25 range for both cases. Read the flap and boot outlines from the selected solid mask. Keep the full-precision volume for deriving the overlaid arrow and paths. [Reference image](evo-wing-flow-comparison.png)

### B. Build one component player and prove it with the wing

**Ownership.** Adapt `subsystems/race-aero.js` and its Evo configuration together. It already owns the precomputed case controls, theme mapping and tracer drawing, and the Evo is its only current caller. Reuse the same subsystem for each new part. Leave `subsystems/aero.js` serving the other stops. The story already supplies a step and an orbit target for each component. [Component loader and visibility](../lib/app/viewer.js) · [Story and disclosure layout](../lib/app/story.js) · [Current CFD player](../subsystems/race-aero.js)

**File contract.** Use one `field.json` and one `<case-id>.bin` per state under `stops/<slug>/cfd/<part>/`. Start with one scalar field per part. The manifest declares the plane, location, cell spacing, dimensions, scalar quantity, shared display range and case IDs. Each case carries its computed paths and guides in vehicle mm. Here is the wing reference header to use in the first round-trip test.

```json
{
  "plane": "xz",
  "originMm": [-3171, 238, 826],
  "cellMm": 28,
  "width": 41,
  "height": 22,
  "quantity": "vertical-speed-over-inlet",
  "range": [-0.25, 0.25],
  "cases": {
    "base": { "lines": [], "guides": [] },
    "flap": { "lines": [], "guides": [] }
  }
}
```

Rows run from bottom to top. Advancing a column always decreases vehicle x. Advancing a row increases z for `xz` or y for `xy`. The origin is the **centre of the first cell**. Use vertical velocity divided by inlet speed for the wing, pressure coefficient for the splitter, and mean-flow speed divided by inlet speed for the wheel views. Each binary is exactly `width * height` bytes in row-major order. Reserve 255 for solid. Quantize the common scalar range into 0…254 with rounding and clamping. Draw solid cells opaquely so the moving part remains legible. A path is an ordered array of `[x,y,z]` points. Give each guide a `kind` of `arrow` or `line` and a `points` array in the same frame. The fixture above illustrates the header. The display assets must contain the measured guide and the paths that the lesson uses. Keep labels in translated stop data. Keep run provenance, input geometry, both-grid results and raw units with the generation tools.

1. Start with `lib/model/part-field.js` and `tests/unit/part-field.test.mjs` for the pure format/mapping logic used by the exporter and player. A tiny asymmetric 3 × 2 fixture should catch a left/right mirror, row flip, misplaced half cell, bad byte count or solid decoded as a field value. Check both plane orientations, endpoints of the colour range, and the generated manifest’s case IDs against the stop config.

### C. Compute the local wing and splitter

**Repeatable offline runs.** Add the local cases behind `part.mjs`. A useful command contract is `node tools/cfd/part.mjs <wing|splitter|w196-wheel|evo-arch> <solve|export>`. These are proposed commands to implement. Each `solve` runs the component’s specified cases/grids into its own ignored output directory. Each `export` validates the complete case set, then publishes the compact display assets to its stop folder. Keep partial runs out of that folder. Check in the small geometry inputs and the generator, so regular builds and CI can use the committed exports without rerunning CFD. Preserve any external input’s source, assumptions and regeneration instructions.

**Local wing.** Build a domain around the wing, its gap above the boot, and the boot surface that feeds the gap. Resolve the hinged or extended portion from a documented profile or label the archived geometry as illustrative. Keep the baseline and changed geometries registered. Use the original full-car baseline’s upstream mean velocity profile to supply the same approach flow to both local runs. Save that small sampled inlet and its station with the case inputs. The current D3Q19 kernel initializes a uniform inlet. If extending it, accept a plane of inlet velocities, apply the existing equilibrium-distribution rule at fluid inlet cells, and retain the uniform default. Verify uniform-plane equivalence on a small grid. Keep enough upstream/downstream clearance for the measured turn to survive moving the boundaries. Compare the new local probe across grids and against A’s reference. If the local result disagrees, investigate inlet position, wing gap and resolution. Keep the archived crop labelled with its original run. [3-D solver](../tools/cfd/lbm3d.mjs)

**Splitter.** Draw two closed nose sections from the same bumper profile and ride height. Extend the lip longitudinally. The current 40 mm travel and 25 mm thickness are illustrative. Start at 5 mm per cell, which gives eight cells of travel and five through the plate, then repeat at finer spacing, for example 2.5 mm. Use `rasterize()` and `createTunnel()` from the existing 2-D model in Node. Allow fluid above and below the lip and continue the underside past the visible crop. Keep the road moving and the local domain larger than the on-screen view. Fix the model Reynolds number across refinements by scaling lattice viscosity with the feature length in cells at the same lattice inlet speed. Sample `cp(c)` on fluid cells beside each face over a stated chord interval and average over settled steps. Trace the two paths from fixed inlet seeds in the mean velocity field. Put the pressure map and old-edge tick in the export. If the face-pressure *change between settings* falls inside the variation, keep the position toggle and describe the visible upper/lower paths. Omit a front-axle load estimate. [Live solver functions](../lib/model/flow.js) · [Lip geometry](../tools/cfd/geometry.mjs)

### D. Compute the two front-wheel experiments

1. Build explicit local solids for the tyre, adjacent body, wheelhouse cavity and flare or fairing. Union the tyre and body only after carving the cavity. The existing filled-column Evo body would seal it. For the Evo use the front-wheel dimensions in `tools/cfd/geometry.mjs` as the starting point. For the W 196 R use the stop photo and body references for the two front-quarter shapes. Record assumed track, tyre and clearance dimensions. Inspect side, plan and cross-section masks before launching a long run. Check the road gap, connected air around the shoulder and a nonzero case-mask difference in the intended region. [Evo voxelizer](../tools/cfd/geometry.mjs) · [W 196 R frame and sources](../stops/w196r/car.js)
2. Use the existing offline 3-D kernel with the same road, inlet speed, yaw, wheel placement, outer boundary locations and tyre-motion model within each pair. Keep the current mirror at the vehicle centre by retaining the inboard strip of domain to y = 0. Cropping the rendered patch is inexpensive. Moving the numerical mirror onto the tyre shoulder would change the experiment. Start with a coarse geometry/debug solve. Refine until the smallest clearance or contour change relevant to the claim spans several cells. Budget 152 bytes per cell for the two D3Q19 population arrays alone before increasing resolution. Keep the region of interest away from the side and outlet boundaries. Run a larger domain once to check sensitivity.
3. Begin with stationary tyres over the moving road and label that simplification in both languages. The 3-D kernel supports a moving-wall term, but the current stepped spinning tyre pumped air artificially. A rotation-specific claim needs a resolved surface, contact treatment and a successful comparison to a moving-ground wheel benchmark. Match physical tyre-road clearance across the two grids. [Wheel modelling note](../tools/cfd/geometry.mjs) · [Experimental wheelhouse flow study](https://www.mdpi.com/1996-1073/12/17/3340)
4. **W 196 R.** Use one matched front wheel with the local exposed and enclosed body shapes. Choose a wheel-height `xy` plane and a downstream station in common exterior air, clear of both solids and the outlet. Fix these in physical mm before evaluating the final pair. As a starting definition, mark the connected band behind the shoulder where mean speed is below 80% of the inlet speed. Record its two lateral edges and width. Use the same threshold and search interval in both cases. Trace air from identical seed positions, export both outlines and wake guides, and have the text describe the observed direction. If the width is ambiguous, inspect the displacement and shape of the wake on the same plane. If neither repeats across grids, revise the domain or measurement and leave this comparison pending.
5. **Evo arch.** Seed a short ribbon just outside the front shoulder. In the fitted-arch case, export its path round the flare into the flank and measure its lateral displacement at a fixed station. For a comparison, change only the outer arch contour around the same tyre. Verify actual clearance on both grids. If the mask remains identical or the wake shift is unresolved, ship the validated fitted-arch path as a single-state lesson. **Follow the air** highlights that path and gives its one-sentence explanation. Label the narrower arch as an illustrative design experiment.

**Numerical acceptance for new runs.** Save the physical domain, spacing, boundary conditions, inlet speed, viscosity, settling time, sample region and reference velocity with each result. After the startup transient, take at least three successive time-window means spanning several flow-through times in total. In 3-D, `fields()` is cumulative over averaged steps. Difference successive weighted sums or accumulate the few local probes by window. Check finite fields, mask alignment and distinct local geometry, then compare the local observable across the two grids, time windows and an enlarged domain. Publish a directional comparison when its sign repeats and exceeds the observed window scatter on each grid. For a wake contour, repeat the check on its position or width and inspect the field itself. Keep the local result attached to the part. Whole-car drag, axle load and top speed each require a whole-car calculation.
